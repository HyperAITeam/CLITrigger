# v0.2.46 — Reliable focus recovery for new terminal forms (Windows desktop)

Release date: 2026-08-05
Previous version: v0.2.45

## TL;DR

Small patch release for the Windows desktop app. It fixes the recurring "can't type into the new terminal form" bug for good: the forced IME reset now cycles the OS window itself (blur→focus) — the only recovery path proven to work — and the three competing focus-rescue mechanisms were unified into one, eliminating a feedback loop that could steal focus right back from the input you just clicked.

## Highlights

### New terminal form focus no longer breaks (Electron / Windows)

- Opening the new terminal form after using an xterm terminal could leave keyboard input dead — clicks landed, but typing (especially with Korean/IME input) went nowhere.
- Root cause: the previous forced reset moved focus around *inside* the webview, which never generates the OS-level `WM_KILLFOCUS`/`WM_SETFOCUS` messages needed to revive a stranded Windows TSF (IME) context. Only a real window blur→focus (like alt-tabbing away and back) recovered it.
- The `ime:reset(force)` bridge now blurs and refocuses the `BrowserWindow` itself, replaying the exact recovery path that was verified working in debug logs.
- Known trade-off: the title bar may flicker inactive for an instant when entering a form. That's the cost of a real OS focus cycle.

### Focus rescue paths unified

- Three independent rescue mechanisms (app-level bridge, form mount, terminal self-recovery) could interfere with each other: a forced handoff momentarily makes the window report "unfocused", which was itself the trigger condition for another rescue — a feedback loop that could blur the input you had just focused.
- All three call sites now go through a single shared handoff module (`ime-handoff.ts`) with an in-flight guard, so only one rescue runs at a time.
